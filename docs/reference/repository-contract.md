# Repository contract

This page describes the current repository-facing contract for the managed bootstrap, optimize-job, and deployment surface.

The authority order is:

1. committed repository files such as `.foundry-opt/registry.yaml` and each selected sidecar
2. the current public runtime and templates in `src/foundry_opt/`
3. reviewed issue input that narrows behavior without widening repository policy

## Managed contract set

| File | Role | Mutation mode |
| --- | --- | --- |
| `.foundry-opt/registry.yaml` | repository-level source of truth for distribution, GitHub wiring, identity mode, and enabled agents | owned |
| `<agent-root>/.foundry/foundry-opt.yaml` | per-agent v2 profile for optimization, verification, deployment, and Foundry target settings | owned |
| `.github/instructions/foundry-opt.instructions.md` | repository instructions that freeze the trust model for standard Copilot | owned |
| `.github/ISSUE_TEMPLATE/foundry-optimize-agent.yml` | managed operator issue form for optimize jobs | owned |
| `.github/workflows/copilot-setup-steps.yml` | setup workflow patched onto the reserved managed contract | shared-template |
| `.github/workflows/foundry-opt-validation.yml` | validation workflow for the managed contract | owned |
| `.github/workflows/foundry-opt-deploy.yml` | registered deployment workflow | owned |
| `.foundry-opt/bootstrap.lock.json` | generated ownership ledger written by repository apply and advanced by evaluation activation | generated |

The exact payload set is defined by the trusted manifest at [`src/foundry_opt/templates/customer-repo/.foundry-opt/managed-payloads.manifest.yaml`](../../src/foundry_opt/templates/customer-repo/.foundry-opt/managed-payloads.manifest.yaml). That manifest is runtime authority, not a customer-repo payload to render.

## `.foundry-opt/registry.yaml`

The registry is the repository-level source of truth for:

- `distribution.repository`, `distribution.channel`, and the exact reviewed `distribution.pin`
- GitHub environment names and the client-id variable name
- the identity mode used by bootstrap and deployment
- the set of enabled agents, each with a stable `agent_id`, managed `root`, and `config_path`

Registered workflows select agents from the registry, not from issue prose. When `repoAgentId` is omitted during registry-managed execution, the runtime requires exactly one enabled agent.

## Per-agent v2 sidecar: `.foundry/foundry-opt.yaml`

Each selected sidecar is `schema_version: 2` and binds one stable `repo_agent_id` to:

- `source_root`, `package_root`, and `editable_paths`
- runtime entrypoint and hosting contract
- Foundry project settings and optional reviewed target
- the baseline model and allowed candidate models
- candidate bounds and decision policy
- hard guardrails
- deployment settings
- verification settings, repository checks, and any activated default evaluator bundle lineage

For current owner workflows, this is the authoritative policy source for optimization and registered deployment.

## `.foundry-opt/bootstrap.lock.json`

The committed lock is generated by repository apply. It is not a rendered template payload.

It records:

- the runtime repository, channel, and exact runtime commit
- every managed file with `ownership_mode`, `owner_scope`, `template_id`, and digests
- adopted GitHub environments and cloud resources
- the tracked sidecar paths
- the last evaluation-activation outcome

The lock is the ownership ledger that lets later repository apply, activation, and rollback prove they are still mutating the same managed contract.

## Managed instructions and issue form

The managed instruction file at [`.github/instructions/foundry-opt.instructions.md`](../../src/foundry_opt/templates/customer-repo/.github/instructions/foundry-opt.instructions.md) tells standard Copilot what is mutable and what is protected.

The managed issue form at [`.github/ISSUE_TEMPLATE/foundry-optimize-agent.yml`](../../src/foundry_opt/templates/customer-repo/.github/ISSUE_TEMPLATE/foundry-optimize-agent.yml) is the public optimize-job input contract.

Current issue-form rules that matter operationally:

- choose a stable `repoAgentId` from the registry, or use an explicit Foundry target only for migration cases
- current evaluator input is exact-ID based
- current dataset input is exact dataset-ID or URI based
- current verification commands are exact `command: ...` lines only
- named `check: ...` entries are reserved for trusted repository profiles and workflows
- the current public form does not expose candidate-model narrowing, even though the parser still accepts a hidden compatibility-only model filter from older issue bodies

Friendly evaluator name or version UX and friendly dataset name or version UX are not part of the current public contract.

## Managed workflows

Setup workflow:

- verifies the exact runtime checkout against `.foundry-opt/registry.yaml`
- installs the CLI and skill
- records trusted bootstrap, broker, and job-state paths
- launches the GitHub broker for trusted issue contexts, or runs offline preflight otherwise

Validation workflow:

- validates the registry and sidecar contract
- verifies the managed runtime and protected runtime paths
- provides the managed validation checkpoint before bootstrap or later review

Deploy workflow:

- expands changed paths to the affected enabled agents
- freezes the selected registry entry and sidecar into a deployment plan
- runs exact-source verification and publish or reconcile from the default branch

Unrelated workflows are not part of the managed payload set unless a reviewed repository plan adopts them explicitly.

## Ownership modes

The runtime uses three ownership modes:

- `owned` - the runtime manages the full file content
- `shared-template` - the runtime applies only the reviewed semantic patch to the reserved target file
- `generated` - the runtime writes the file from applied state instead of a template payload

If repository apply cannot safely replace a shared target, it writes a `.foundry-proposed` sibling for human review instead of overwriting ambiguous customer edits.

## Legacy and migration support

Legacy behavior still exists only where compatibility requires it:

- `.github/foundry-opt.lock.yml` remains readable for migration and explicit `foundry-opt bootstrap verify --pin ...`
- schema-version-1 sidecars still load through compatibility conversion to the v2 shape
- explicit Foundry targets remain valid for migration issues before the registry-managed contract is fully adopted

Registered workflow execution does not accept explicit Foundry targets. Once a repository is registry-managed, `.foundry-opt/registry.yaml` plus the selected sidecar become the only deployment authority.
